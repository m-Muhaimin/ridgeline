## 6. Findings

### 6.1 Root `tsc` now compiles `apps/web` — works, but by luck of `skipLibCheck`
Root `tsconfig.json` has **no `include`/`files`**, so its program globs the whole repo. Verified with `tsc --noEmit --listFiles`:

- **4 of my source files are in the root program**: `app/layout.tsx`, `app/health/page.tsx`, `next.config.ts`, `postcss.config.mjs` (via `allowJs`).
- **3 generated `.d.ts` too**: `next-env.d.ts`, `.next/types/routes.d.ts`, `.next/types/root-params.d.ts`.
- **362 files from `apps/web/node_modules` are ALSO in the root program.** TypeScript's default `exclude` is `["node_modules", …]`, which matches only the *top-level* `node_modules` — it does not exclude **nested** ones. Root `exclude` is unspecified, so nothing compensates.

So the root program now contains **two copies** of `@types/react`, `react-dom`, and `csstype`, plus all of Next's types. This is **0 errors today only because root sets `skipLibCheck: true`**, which suppresses errors *inside* `.d.ts` files.

I specifically tested the scariest case: `next-env.d.ts` line 3 is `import "./.next/types/routes.d.ts";`, a path that **does not exist on a fresh clone**. With `apps/web/.next` moved away, root `tsc` still exited **0** — because `skipLibCheck` skips checking `next-env.d.ts` itself.

**Implication for tasks 2–10:** root `tsc` is safe, but the margin is thinner than it looks. If anything ever flips `skipLibCheck`, or a future task's code depends on a compiler setting root lacks, the **root** gate will break on `apps/web` code. Cheap insurance for task 10 (which owns root `tsconfig.json`): add `"exclude": ["node_modules", "apps/web/node_modules", ".next"]`. I did **not** touch the root tsconfig — out of scope for this task and explicitly gated to task 10.

### 6.4 Background-process cleanup: `kill $!` leaves an orphan — needs `taskkill //T`
My first three runtime probes left a **stray `next dev` listening on `:3001`** after cleanup. Two separate causes, both worth knowing before anyone scripts repeated runtime checks on this box:

1. **`kill "$PID"` is not enough.** `npm --prefix apps/web run dev` spawns `npm` → `next dev` → a Turbopack worker. `kill` terminates the `npm` wrapper (the PID `$!` gives you) and leaves the grandchild holding the port. `taskkill.exe //F //T //PID <npm-pid>` is required. Confirmed: PID 7924 (`next dev`, 252 MB) plus its child 8316 survived `kill` and were only reaped by `taskkill //T`.
2. **`netstat` and `taskkill` are not on PATH in this bash.** They live in `C:\Windows\System32`. My first cleanup attempts used `taskkill //F //T //PID … 2>/dev/null`, which **silently did nothing**, and `netstat` with `2>/dev/null` likewise — so I initially reported "no listeners, ports clean" while a server was still running. That reading was a false negative. Correct form: `export PATH="$PATH:/c/Windows/System32"` first.

Net effect on the results: probes 2–4 overlapped a previous probe's still-running server (hence transient `EADDRINUSE` on `:3000` and `24678`). **All findings are unaffected** — every run executed the identical code from the identical files, and the decisive comparison in §6.3 (direct `:3000` vs proxied `:3001`) returned byte-identical responses from two *different* server instances, which is a stronger result than a single-instance comparison. Final state is verified clean.
